# Data sources: Brønnøysundregistrene — verified findings

Technical note for Peerless. Everything below has been tested against actual calls, not read out of the documentation. Test companies: 979 607 008 and 923 609 016.

---

## Sources

| Source | Content | Cost | Status |
|---|---|---|---|
| Enhetsregisteret (Central Coordinating Register for Legal Entities) | Company data, industry code, employees, roles, statement of purpose | Free, bulk download | Not tested in detail |
| Regnskapsregisteret (Register of Company Accounts) — key figures | Condensed income statement and balance sheet, most recent year | Free, open API | Verified |
| Regnskapsregisteret — document | Complete annual accounts as PDF, all years | Free, open API | Verified — **raster images only, see below** |
| Regnskapsregisteret — restricted section | All accounting figures, history, group accounts | Chargeable / public authorities | Not investigated — **now the highest-value open question** |

---

## Endpoints

```
GET /regnskapsregisteret/regnskap/{orgnr}
    → key figures, most recently filed year. XML or JSON.
    Parameters: year, regnskapstype (selskap|konsern)

GET /regnskapsregisteret/regnskap/{orgnr}/{id}
    → a single filing by id

GET /regnskapsregisteret/regnskap/aarsregnskap/kopi/{orgnr}/aar
    → JSON list of available years
    Example: ["2011","2012", ... ,"2025"]

GET /regnskapsregisteret/regnskap/aarsregnskap/kopi/{orgnr}/{aar}
    → the annual accounts as PDF
```

Base: `https://data.brreg.no`. No authentication on any of these.

## The annual accounts document — every page is an image

**This is the single most consequential finding in this note.** The PDFs served by the `aarsregnskap/kopi` endpoint contain no text layer at all. Not in older filings, not in recent ones. Every page is one full-page raster image.

**Evidence.** All 15 available years for 979 607 008 (2011–2025), 264 pages in total. Every page's content stream is 33 bytes and identical in form:

```
q 1728 0 0 2312 0 0 cm /Im1 Do Q
```

That instruction draws one image scaled to the page. There is nothing else on any page: zero text-showing operators, zero font resources, no form fields, no annotations. Total extractable characters across all 264 pages: **zero**. Confirmed independently with PyMuPDF, with pdfplumber, and by inspecting the raw PDF structure. The second test company, 923 609 016, shows the same pattern in its raw structure (286–396 image objects per filing, no font resources).

**Consequence: every figure not available from the key figures API requires OCR.** There is no rule-based text extraction path, because there is no text to parse.

**What the documents visually contain** (readable by eye, and recoverable only through OCR):

*Part 1 — generated by Brreg.* A fixed monospace layout, three pages, identical in structure for all companies, produced from the filed data. General information, the complete income statement, the complete balance sheet, note disclosures. This is still the part extraction should target — it is just an image of a fixed layout rather than the layout itself.

*Part 2 — the company's own signed annual accounts.* Varies with the accounting firm's template. Often the auditor's report and an electronic signature page.

**Every document carries a prior-year column.** Two documents give four years. Confirmed in the 2025 filing, which states: "År 2024: Tall er hentet fra elektronisk innlevert årsregnskap fra 2025."

**Content beyond the API** (present in the images, reachable only via OCR): cost of goods sold, personnel costs, depreciation, impairment, other operating expenses, sales revenue, trade receivables, other receivables, bank deposits, trade payables, tax payable, public duties payable, debt to credit institutions, intangible assets itemised.

**Notes:** full-time equivalents to one decimal, personnel costs split into salary / employer's national insurance contribution / pension / other benefits, the depreciation schedule, pledged assets, intra-group balances. Older annual accounts may additionally carry a full shareholder register with ownership stakes.

## Pitfalls — all observed

**The document contains no text.** See the section above. This invalidates any design that assumes rule-based parsing of the filed accounts.

**A browser will show you text that is not in the file.** Chromium-based browsers — Chrome, Edge, Vivaldi — run on-device OCR on scanned PDFs as an accessibility feature. Opening a filing and pressing Ctrl+A or Ctrl+F therefore produces selectable, searchable text, which makes the document look text-bearing when it is not. **Never verify the presence of a text layer in a browser.** Use a library that reads page content directly.

**OCR output carries character substitutions.** Observed across two engines on the 2025 filing for 979 607 008: `이` in place of `0`, a Cyrillic `Р` closing `RESULTATREGNSKAР`, `o` for `0` and `l` for `1` in figures (`-1 541 oo9`, `Side l av 3`), spurious spaces inside words (`Organisas jonsnr`, `finanskos tnader`), and Norwegian diacritics lost throughout (`Belop`, `Lonnskostnad`, `Arsresultat`) by engines without a Norwegian model.

**But the dominant failure mode is digit segmentation, not character recognition.** The costly errors were figures split or merged wrongly: `722 632 310` for `72 632 310`, `8 335 514` for `833 514`, `555 826 660` for `55 582 660`. These are assembly errors in the extraction code rather than model errors, which means they are ours to fix — and because they are wrong by orders of magnitude, they are loud rather than silent.

**Recognition confidence is not a quality signal.** A generic engine reported mean confidence 0.974 on these pages while producing every error above. The data quality flag must be derived from arithmetic checks, never from confidence.

**The year parameter is ignored.** `?år=2023` returned the 2025 filing with an identical `id` and `regnskapsperiode`, and status 200. Nothing fails. An implementation that trusts the parameter builds a trend of identical years without an error. **Always match on `id` or `regnskapsperiode`, never on the year requested.**

**An empty element is not null.** `<langsiktigGjeld/>` came back empty for 979607008, while the difference between `sumGjeld` 23 309 355 and `sumKortsiktigGjeld` 18 676 023 shows the amount is in fact 4 633 332. **Derive missing components from the difference against the stated total.**

**A filing's own subtotals do not always sum exactly, and this is not an error.** The register presents whole kroner rounded from underlying øre, so a stated subtotal can legitimately differ from the sum of its components. Verified by reading the rendered 2025 filing for 979607008 by eye: `Sum inntekter` is stated as 72 632 310 while its components give 72 632 311; `Årsresultat` is stated as −1 541 009 while the lines above give −1 541 008; `Sum gjeld` is stated as 23 309 355 while 4 633 331 + 18 676 023 gives 23 309 354. The same one-krone gaps appear in the 2024 column. Meanwhile `Sum kostnader`, `Sum kortsiktig gjeld` and `Sum egenkapital` are exact, and the balance sheet balances exactly at the top. **An internal check demanding exact equality would reject valid filings.**

Note also that the API's *derived* langsiktig gjeld — `sumGjeld` minus `sumKortsiktigGjeld`, giving 4 633 332 — differs by one krone from the 4 633 331 the document states. Neither is wrong; they are the same figure reached by two roundings.

**Reconcile with two different rules, neither of them exact equality.** Between sources — document against API — use a proportional tolerance, because companies reporting in thousands or millions introduce real scaling error. For 923609016, `sumEiendeler` deviated from `sumEgenkapitalGjeld` by 1 000 000, because the company reports in millions of USD. Within a document, use a **tight absolute bound of a few kroner**: wide enough for the rounding above, far too narrow to admit a recognition error. Observed OCR failures on this filing produced 722 632 310 for 72 632 310 and 8 335 514 for 833 514 — wrong by orders of magnitude, and caught by any absolute bound. A proportional tolerance would have hidden them.

**Currency varies.** 923609016 reports in USD. **Must be filtered before comparison.**

**Accounting rules vary.** `regnskapslovenAlminneligRegler` versus `forenkletAnvendelseIFRS`. **These do not belong in the same peer group.**

**`oppstillingsplan` says nothing about size.** The value `store` occurred on a company with 72 million in revenue and `smaaForetak: true`. **Use `smaaForetak` and `regnskapsregler` for comparability, not `oppstillingsplan`.**

**Small companies do not yield fewer fields.** The field set was identical for a small AS and for an ASA. **The key figures list holds for the whole population.**

**Older documents are worse scans, not a different kind of document.** 2011 for 979607008 is an image of a paper form, with skewed pages and handwritten signatures. Recent filings are clean renderings of a generated layout. Both are images; expect OCR accuracy to differ sharply between them.

**Companies change name.** The same organisation number was Ekstra Ressurs AS in 2011 and Statement AS in 2025. **Match on organisation number only.**

**The field name `sumInnskuttEgenkaptial` is misspelled in the API.** Do not correct it in the parser.

## OCR feasibility — first measurement

Run on the 2025 filing for 979 607 008: the three generated pages rendered at 300 DPI, recognised with a generic ONNX engine with no Norwegian model and no tuning, then assembled into rows by vertical position and into figures by horizontal adjacency. Checked against the key figures API, which is authoritative.

**11 of 14 figures recovered exactly.** The three failures were all digit assembly — `722 632 310` for `72 632 310`, `8 335 514` for `833 514`, and `Sum gjeld` missed entirely — not character recognition.

**Position-based row grouping reconstructed label-to-value rows correctly**, across both the current and prior-year columns. `Salgsinntekt → [71 987 157, 66 799 459]` and similar throughout. This was the structural premise behind targeting the generated section, and it holds.

**Known headroom, none of it exotic:** a Norwegian-capable model, a digit-restricted recognition pass over the numeric columns to eliminate `o`/`0` and `l`/`1` confusion, and column boundaries calibrated on x rather than inferred from gaps — which is where all three remaining failures occurred.

**Not yet measured:** the older paper-form scans. 2011 for this company is visibly far worse than the clean renderings of recent filings, and its accuracy should be expected to differ sharply.

## Design implications

The peer group is built on the key figures API, which is free, structured and fast. Nothing in peer group assembly depends on documents.

Document figures require an OCR pipeline: render the page at high resolution, recognise words with their bounding boxes, group them into rows and columns by position, then parse. The generated section has a fixed layout, so column boundaries can be calibrated once and reused across all companies — this is what makes the problem tractable rather than open-ended.

Because OCR is slow, extraction cannot run inside a user request. Documents are extracted by a batch job that pre-warms the covered industries, and the result is stored permanently. Lazy on-demand extraction is not viable.

Every extracted figure passes an internal consistency check within a tight absolute bound of a few kroner before it is stored, and a proportional reconciliation against the API figures where those exist. A failure blocks the filing rather than degrading the analysis silently. The data quality flag shown with each filing is derived from these arithmetic checks, not from OCR confidence.

History is fetched every other year, since each document carries a prior-year column.

The comparability filter runs before classification: currency, accounting rules, `smaaForetak`, `avviklingsregnskap`, accounting period, `regnskapstype`.

## Open questions

- **OCR accuracy on the older paper-form scans.** Recent filings are measured at 11 of 14 figures exact, untuned — see the section above. The 2011-era scans are a different problem and are not yet measured at all. Their accuracy determines how far back multi-year trend can honestly reach.
- Whether a digit-restricted recognition pass over the numeric columns materially reduces substitution errors, and whether calibrated column boundaries eliminate the assembly failures.
- The price of the chargeable subscription to annual accounts data, which provides history, more figures and group accounts. **If it returns structured figures, it removes the need for OCR entirely** — worth establishing before building the pipeline.
- Does the key figures API expose historical filings by `id`, or only the most recent one? This determines whether older OCR output has an independent total to reconcile against, or only internal consistency.
- Exact URLs and filter parameters for bulk download from Enhetsregisteret.
- Terms of use and any rate limits on systematic retrieval at volume.
